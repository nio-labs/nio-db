NioDB Guide

The Agentic DB that works. A single-binary, ultra-lightweight database with pure-Rust SIMD vector search, multi-agent multiplexing, and natural-language query planning.

1. Quickstart & Installation

NioDB runs as a standalone single-binary server. Zero heavyweight dependencies, zero external database servers.

Run instantly via npx

npx @nio-labs/nio-db

Or build and run from source

npm install --omit=optional
cargo build --release --locked
node bin/niodb.cjs

On first launch, NioDB initializes a local data directory (default ./nio-db) and listens on http://127.0.0.1:7432.

CLI Flag / OptionDescription
--dir <path>Set custom database storage directory.
--listen <ip:port>Override local bind address (default 127.0.0.1:7432).
--seed-demoAdd the starter demo set to an existing database once.
--no-demoSkip demos when creating a new database.
--yesAccept all first-run setup defaults without prompts.
NIODB_NO_INSTALL_NIO=1Skip automatic Nio CLI installation.
NIODB_CORS_ORIGINSComma-separated list of allowed CORS origins.

Your starter demo

A new database includes one welcome record in the demo collection, one niodb_demo user, one welcome.txt file in the demo bucket, one demo.ping TypeScript worker, and one starter event. File storage also creates a file metadata record.

The worker demonstrates fetch() by calling this server's /health REST endpoint. It runs once when the demos are created; publishing another demo.ping event runs it again. The starter event appears when you connect to the live stream. Other events are delivered live without historical replay.

The demo user's randomly generated password is saved in nio-db/demo-user.json (or your custom data directory). Use this file to test user login. A successful login returns an app-user session token; the console's Test Login action keeps your console bearer token unchanged.

Demos are created once. Restarting does not duplicate them or recreate examples you delete. Existing databases retain their data; start with --seed-demo to add the starter set, or use NIODB_SEED_DEMO=1 with the development launcher. To create a database without demos, use --no-demo or NIODB_NO_DEMO=1.

2. Client SDKs

NioDB provides zero-dependency, ultra-lightweight client SDKs for JavaScript/TypeScript and Python.

JavaScript / TypeScript (@nio-labs/nio-db.js)

npm install @nio-labs/nio-db.js

Standard JSON Document Operations (Non-Vector)

import { createNioDB } from "@nio-labs/nio-db.js";

// Initialize with client-token and secret-token combination (or direct token)
const db = createNioDB({ 
  url: "http://127.0.0.1:7432", 
  clientToken: "niodb_client_...",
  secretToken: "niodb_secret_..." 
});
const users = db.collection("users");

// 1. Insert Document (with optional TTL in seconds)
const user = await users.insert({ name: "Alex Rivera", role: "admin", status: "active" }, { ttl: 86400 });

// 2. Read & List with Pagination
const profile = await users.get(user.id);
const page = await users.find({ limit: 25 });

// 3. Update / Patch Document
await users.update(user.id, { role: "superadmin", last_login: Date.now() });

// 4. Bulk Operations (Insert, Update, Delete)
await users.insertMany([
  { name: "Beatrix", role: "developer" },
  { name: "Carlos", role: "analyst" }
]);
await users.updateMany([{ id: "art_1", status: "verified" }]);
await users.deleteMany(["art_2", "art_3"]);

// 5. Delete Document
await users.delete(user.id);

// 6. SQL Query Studio
const { items } = await db.query("SELECT * FROM users WHERE role = 'admin'");

Vector & Semantic Search (Optional)

// Pure-Rust SIMD Cosine Distance Vector Search (No external vector DB needed)
const knowledge = db.collection("knowledge_base");
await knowledge.insert({
  text: "High-performance vector embeddings",
  embedding: [0.082, 0.491, 0.122, 0.941]
});

const matches = await knowledge.searchVector({
  vector: [0.082, 0.491, 0.122, 0.941],
  topK: 5,
  minScore: 0.75
});

3. Authentication & Tokens

NioDB uses standard Bearer tokens for all protected HTTP endpoints.

During initial setup, two secure credentials are created in your data directory: client-token and secret-token. Bearer authentication supports combining both credentials (<client-token>:<secret-token>) or using your client token directly.

CLIENT_TOKEN=$(cat ./nio-db/client-token)
SECRET_TOKEN=$(cat ./nio-db/secret-token)
NIODB_TOKEN="${CLIENT_TOKEN}:${SECRET_TOKEN}"

curl http://127.0.0.1:7432/api/v1/status \
  -H "Authorization: Bearer $NIODB_TOKEN"
Security Tip: Combining client-token:secret-token verifies both public client identity and private signing authority. For client web/mobile applications, register end users via POST /auth/register and use scoped session tokens from POST /auth/login.

4. Records, CRUD & Bulk Operations

A record is a JSON document stored in an append-only collection. NioDB assigns unique IDs, revisions, timestamps, and verifies SHA-256 integrity. Full CRUD and bulk batch operations are supported.

POST /api/v1/records — Insert Record

curl -X POST http://127.0.0.1:7432/api/v1/records \
  -H "Authorization: Bearer $NIODB_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: task-create-001" \
  -d '{
    "collection": "tasks",
    "data": {
      "title": "Review release build",
      "priority": "high",
      "ttl": 3600
    }
  }'

GET /api/v1/records/:id — Read Record

curl http://127.0.0.1:7432/api/v1/records/art_123 \
  -H "Authorization: Bearer $NIODB_TOKEN"

PATCH /api/v1/records/:id — Update Record

Atomically updates and merges record data, incrementing the revision counter.

curl -X PATCH http://127.0.0.1:7432/api/v1/records/art_123 \
  -H "Authorization: Bearer $NIODB_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "data": {
      "priority": "urgent",
      "status": "in_progress"
    }
  }'

DELETE /api/v1/records/:id — Delete Record

Appends a tombstone deletion event to the journal, removes from in-memory index, and cleans the artifact projection.

curl -X DELETE http://127.0.0.1:7432/api/v1/records/art_123 \
  -H "Authorization: Bearer $NIODB_TOKEN"

POST /api/v1/records/bulk — Bulk Operations (Batch)

Perform high-throughput bulk inserts, updates, and deletes in a single request.

1. Bulk Insert:

curl -X POST http://127.0.0.1:7432/api/v1/records/bulk \
  -H "Authorization: Bearer $NIODB_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "collection": "tasks",
    "action": "insert",
    "records": [
      { "title": "Index vector embeddings", "status": "pending" },
      { "title": "Run storage compaction", "status": "pending" }
    ]
  }'

2. Bulk Update:

curl -X POST http://127.0.0.1:7432/api/v1/records/bulk \
  -H "Authorization: Bearer $NIODB_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "action": "update",
    "records": [
      { "id": "art_1", "data": { "status": "completed" } },
      { "id": "art_2", "data": { "status": "completed" } }
    ]
  }'

3. Bulk Delete:

curl -X POST http://127.0.0.1:7432/api/v1/records/bulk \
  -H "Authorization: Bearer $NIODB_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "action": "delete",
    "ids": ["art_1", "art_2"]
  }'

GET /api/v1/records — List & Pagination

curl "http://127.0.0.1:7432/api/v1/records?collection=tasks&limit=50" \
  -H "Authorization: Bearer $NIODB_TOKEN"

List requests support page limits from 1 up to 1,000 records per request, using cursor-based pagination.

6. SQL Query Studio (AlaSQL Engine)

Run safe, restricted, parameterized SQL queries across your collections. Collections automatically act as SQL tables with top-level JSON fields exposed as queryable columns.

POST /api/v1/query — Execute SQL

curl -X POST http://127.0.0.1:7432/api/v1/query \
  -H "Authorization: Bearer $NIODB_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "sql": "SELECT id, title, status FROM tasks WHERE status = ? ORDER BY id DESC LIMIT 50",
    "parameters": ["pending"]
  }'

TypeScript Event Workers

Workers run JavaScript or TypeScript whenever a matching event is published. They can call REST APIs using Node's built-in fetch(), read environment variables, and use Node modules. Each source file must export a default function that receives the event.

Use Console → Events & Webhook → Event Workers to register a worker, view its source, format the code, or save updates. The REST endpoints below provide the same operations.

Event input and execution

type LiveEvent = {
  id: string;
  name: string;
  actor: string;
  created_at: string;
  data: Record<string, unknown>;
};

export default async function (event: LiveEvent) {
  // Your code runs for each matching published event.
}

Set event_name to an exact name such as demo.ping, or * to receive all events. Worker registration, details, updates, deletion, and event publishing require a backend secret bearer credential (secret token or client:secret combination).

Workers require Node 22+ with stripTypeScriptTypes support. They run as trusted server code in a separate process with a 5-second total timeout, a 64 MiB V8 heap, and at most 2 concurrent executions. Source is limited to 32 KiB. They inherit the server's environment and filesystem/network access. Import Node modules with node: specifiers; relative imports from a worker's source are not supported.

Publishing returns before workers finish. Worker output is not returned to the publisher or displayed in the console. Failures and capacity skips are reported in the server terminal. Workers do not retry automatically; make external side effects idempotent using event.id.

Example 1: GET a REST endpoint

This is the starter worker. Save it as worker.ts and subscribe to demo.ping. Change the URL if your server uses another port.

type Event = { id: string; name: string; data: unknown };

export default async function (event: Event) {
  const response = await fetch("http://127.0.0.1:7432/health", {
    signal: AbortSignal.timeout(3000),
  });
  if (!response.ok) {
    throw new Error(`Health API returned ${response.status}`);
  }
  const health = await response.json();
  // Use the returned JSON in your own integration.
}

Example 2: POST JSON with API authentication

Subscribe to order.created. Configure ALERT_API_URL and ALERT_API_TOKEN in the environment when starting NioDB. Replace these with your API's URL and credential. The receiving API must support your chosen idempotency header.

type OrderEvent = {
  id: string;
  data: { order_id: string; total: number };
};

export default async function (event: OrderEvent) {
  const url = process.env.ALERT_API_URL;
  const token = process.env.ALERT_API_TOKEN;
  if (!url || !token) throw new Error("Configure the alert API");

  const response = await fetch(url, {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      Authorization: `Bearer ${token}`,
      "Idempotency-Key": event.id,
    },
    body: JSON.stringify({
      order_id: event.data.order_id,
      total: event.data.total,
      message: "Order received",
    }),
    signal: AbortSignal.timeout(3000),
  });
  if (!response.ok) {
    throw new Error(`Alert API returned ${response.status}`);
  }
}

Example 3: Fetch a NioDB record

Subscribe to record.created and publish its record_id in the event data. Set NIODB_BASE_URL and NIODB_TOKEN in the server environment. Credentials are not automatically injected into workers.

type RecordEvent = { data: { record_id: string } };

export default async function (event: RecordEvent) {
  const token = process.env.NIODB_TOKEN;
  if (!token) throw new Error("Configure NIODB_TOKEN");
  if (typeof event.data.record_id !== "string") {
    throw new Error("Event is missing record_id");
  }
  const base = process.env.NIODB_BASE_URL || "http://127.0.0.1:7432";
  const id = encodeURIComponent(event.data.record_id);
  const response = await fetch(`${base}/api/v1/records/${id}`, {
    headers: { Authorization: `Bearer ${token}` },
    signal: AbortSignal.timeout(3000),
  });
  if (!response.ok) {
    throw new Error(`Record API returned ${response.status}`);
  }
  const record = await response.json();
  // Send selected record fields to your integration here.
}

Register and trigger a worker

Save one of the examples to worker.ts. This command safely encodes its source into JSON. The example subscribes to demo.ping; use the appropriate event name for other examples.

export NIODB_TOKEN="your-backend-secret-or-client:secret"

node -e 'const fs = require("node:fs"); process.stdout.write(JSON.stringify({event_name: "demo.ping", source: fs.readFileSync("worker.ts", "utf8")}))' > worker.json

curl -X POST http://127.0.0.1:7432/api/v1/events/workers \
  -H "Authorization: Bearer $NIODB_TOKEN" \
  -H "Content-Type: application/json" \
  --data-binary @worker.json

curl -X POST http://127.0.0.1:7432/api/v1/events \
  -H "Authorization: Bearer $NIODB_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name":"demo.ping","data":{"message":"Test REST fetch"}}'

List, inspect, update, and delete

Replace wrk_123 with the ID returned when registering. Listing returns worker metadata; getting a worker by ID includes its source. PATCH accepts source, event_name, or both, and preserves the worker's ID and creation details.

curl http://127.0.0.1:7432/api/v1/events/workers \
  -H "Authorization: Bearer $NIODB_TOKEN"

curl http://127.0.0.1:7432/api/v1/events/workers/wrk_123 \
  -H "Authorization: Bearer $NIODB_TOKEN"

# Edit worker.ts, then generate an update payload.
node -e 'const fs = require("node:fs"); process.stdout.write(JSON.stringify({source: fs.readFileSync("worker.ts", "utf8")}))' > worker-update.json
curl -X PATCH http://127.0.0.1:7432/api/v1/events/workers/wrk_123 \
  -H "Authorization: Bearer $NIODB_TOKEN" \
  -H "Content-Type: application/json" \
  --data-binary @worker-update.json

curl -X DELETE http://127.0.0.1:7432/api/v1/events/workers/wrk_123 \
  -H "Authorization: Bearer $NIODB_TOKEN"

15. Resource Limits & Capacities

NioDB offers generous resource limits while maintaining sub-millisecond local in-memory execution and minimal disk footprint.

Resource Supported Limit Details
Records Capacity Millions of records (16 MiB per record, 64 GiB+ journal) Unbounded in-memory pure-Rust BTree indexing with in-place zero-downtime atomic vacuum compaction.
Pagination Up to 1,000 items per page Fast cursor-based pagination across all collection and file list endpoints.
Vector Embeddings SIMD Cosine Distance (Arbitrary dimensions) Sub-millisecond pure-Rust dot product search over vector embeddings with zero external C++ vector DBs.
SQL Queries 64 KiB input, 1,000 output rows, 15s timeout Restricted read-only SQL with 64 MiB query execution buffer powered by bundled AlaSQL engine.
Nio Natural Query 4 concurrent requests, 60s default timeout (1–300s) Bounded natural language query planning via Nio CLI.
Files & Blobs 64 MiB per file, 100 GiB per workspace, 1,000,000 files Content-addressable storage with SHA-256 deduplication and Range request support.
Users & Sessions 100,000 users, 1,000,000 active sessions Salted PBKDF2 hashing, 7-day bearer sessions with instant revocation across restarts.
Live Events 64 KiB payload, 100/sec, 1,024-event buffer Server-Sent Events (SSE) broadcast channel with gap detection.
Webhooks & Workers 64 webhooks, 64 TypeScript workers HMAC-SHA256 signed deliveries and isolated Node worker processes.
